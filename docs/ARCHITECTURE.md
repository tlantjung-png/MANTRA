# Architecture Guide

## High-Level Design

The system is organized into four conceptual layers that isolate concerns and allow extension without changing core logic.

The core layer holds orchestration and state management. It depends only on abstractions, never on concrete components. Its main pieces are the orchestrator loop, the context manager, the knowledge assembler, the approval policy, and the event bus.

The interface layer declares those abstractions in a dedicated types module: language model clients, sandboxes, tools, evaluators, loggers. Each contract is a small abstract class with a normalized data shape. The event bus is a concrete class rather than an abstract contract.

The implementation layer supplies interchangeable concrete components for each abstraction: two language model clients (a chat-completions client and an offline scripted client), two sandboxes (host directory and container), a set of file, command, search, extraction, tree-query, and web tools, two evaluators, and one structured logger.

The outer layer provides assembly, configuration loading, and the user-facing entry points for interactive and headless operation. The registry maps configuration names to implementation classes and validates them at startup. The layers are conceptual rather than separate directories: contracts live in the types module, concrete components live in modules under the core package, and the entry points are the headless runner and the interactive console modules. The console is a facade over focused modules: presentation rendering, shared primitives such as menus and secret readers, the completion engine, the command surfaces, and the session state itself, which is composed from mixins covering mentions, goals and todos, usage and compaction, persistence, workspace inspection, and endpoint switching; every moved name is re-exported by the facade so callers and test seams are unchanged.

The central orchestrator is the only stateful component in the core. It is built via dependency injection with fully constructed collaborators and does not import concrete implementations. New clients, sandboxes, tools, evaluators, or loggers can be added by implementing an interface and registering the implementation, without modifying the core.

## Module Interactions

A task enters through either the interactive console or the headless runner.

The console maintains a long-lived session that reuses the same sandbox directory, context manager, approval policy, and conversation across turns. The headless runner builds a fresh sandbox for each invocation and maps approval modes to non-interactive forms, since no operator is present to answer prompts.

The orchestrator seeds history, requests a response, and dispatches approved tool calls. Tool execution is delegated to the sandbox, and the resulting observation is appended to history. Tool-call arguments are validated and repaired before execution; repairs that succeed are logged, and unrepairable arguments are returned to the model as an error observation with the expected schema. Usage metadata is accumulated for accounting. The loop ends on a final answer, step limit, abort, or error, after which the evaluator inspects the sandbox and the logger records the outcome. An evaluation is always produced, even after errors, and cleanup is attempted in all cases. The event bus distributes lifecycle events to optional observers, isolating observer failures from the run.

The orchestrator also enforces intent-based loop breaking. Repeated identical tool calls are blocked after a bounded number of attempts; a single identical retry after a transient failure stays allowed; and a successful write or edit invalidates earlier read counters so the natural verify step after a change still runs.

Conversation history is owned by a dedicated manager that enforces limits on message count and total characters. The initial system prompt and task are pinned, and the oldest complete turn is removed first, so tool results are never orphaned. Seeding caps both the system prompt and the task before insertion, and oversized single messages are truncated with space reserved for the system prompt. When the budget is still exceeded, the manager repeatedly truncates the largest message or removes additional turns until within budget.

System prompt assembly merges the base instruction, environment facts, known-failure knowledge, durable per-workspace memory, and repository-specific instructions. Environment facts include date, operating system, shell, interpreter version, workspace location, and version-control branch and dirty state. Each source is capped, durable memory retains the tail of the file to preserve recent entries, and the total assembled prompt is capped. The cap is re-applied after per-turn additions such as standing goals, todo checklists, and attached skills.

Component assembly is performed by a registry that maps short names from configuration sections to concrete classes. The registry validates unknown names and unknown keys at startup, validates that required constructor parameters are present, shares a single edit ledger across file tools, deduplicates tools that resolve to the same implementation, and normalizes tool-name aliases, including legacy aliases for the document-extraction tool and the web-fetch tool.

## Key Decisions and Trade-Offs

Third-party dependencies are kept minimal for core operation: one XML-parsing library serves the document-extraction tool, and everything else — networking, process execution, terminal handling — relies on the standard library. An optional parsing library is required only for the alternative configuration format. This reduces installation drift at the cost of reimplementing some utilities.

Isolation is offered at two levels. A host directory sandbox executes directly in a workspace folder for speed during trusted development. A container-based sandbox manages a disposable container via the container runtime interface for stronger isolation. Neither is presented as a complete security boundary. Both enforce path confinement via resolved path checks at every file and directory operation and check each component of newly created parent chains for symbolic links, including on the fallback write path which re-validates immediately before writing. The host execution path also blocks traversal, encoded traversal, shell expansions, and home-directory expansion in commands, caps execution output on byte boundaries, and strips credential-shaped variables from the child environment. Both host execution paths, foreground and background, spawn their child in a dedicated process group, and every kill routes through a single tree-kill helper, so a timeout, abort, or operator kill removes descendants as well as the shell. The container timeout path signals only children of the keeper process so the container survives for later calls. Process-group spawning, capped incremental pipe reading, and process-tree killing live in one shared process-utility module used by every execution path; verified stale-lock removal used by the persistence stores lives in one shared lock module; and repository-address and commit validation used by both sandboxes lives in one shared URL-checking module, so these safety-critical behaviors have exactly one implementation each. File writes stage through a uniquely named temporary file before the atomic replace, eliminating the predictable staging path a concurrent process could otherwise win a race on. Large command output spilled to temporary files uses owner-only permissions and is pruned by age and count.

The terminal input layer is byte-explicit on the streaming decoder. A lone escape becomes the escape action, the delete byte maps to the backspace action, control-one-byte ranges are dropped rather than inserted as printable text, and the modifier parameter on an arrow-key sequence is decoded into the corresponding key modifiers so shifted and control-arrow bindings work uniformly. Bracketed pastes are bounded in memory and delivered as a single paste event with newlines intact; an unterminated paste is cut off at the cap rather than buffered without limit. Prompt submission during a running turn is serialized through the application lock, so the busy check and the queue write cannot interleave between the turn-ending and turn-starting paths.

The screen is composed as a full cell grid, diffed against the previously shown grid, and only changed cells are written. Because nothing is painted at a stale absolute position by a background thread, a resize is simply a full reflow and interleaved output can never tear a frame.

Streaming is optional and callback driven. When a delta handler is supplied, content fragments are delivered incrementally, and tool-call deltas are accumulated by index before being assembled into complete invocations. The parser tolerates occasional malformed fragments but limits both consecutive and total malformed fragments, caps total streamed content and individual tool-argument size, and bounds single-line buffers without line breaks.

Approval is modeled as a separate policy with four modes that are evaluated per tool call. Read-only operations are always allowed. The confirmation prompt is supplied by the front end, keeping the policy independent of terminal handling. Positive answers can be remembered for the remainder of the session on a per-tool key basis. Wrapper invocations are classified by their inner command to avoid double counting, and interpreter one-liners are gated behind explicit confirmation because their payload is invisible to the pattern screen. Classification fails closed to explicit confirmation for unknown mutating tools and for internal errors. Interactive prompts are serialized through a dedicated lock so concurrent requests cannot overwrite each other, and the orchestrator restores the sandbox abort slot after each run so reused sandboxes do not leak cancellation state.

Persistence is file-based and atomic. Settings, credentials, workflows, and session transcripts are written via uniquely named temporary files with restricted permissions and then moved into place, with quarantine handling for corrupted files under collision-free backup names and verified stale-lock handling for concurrent access. Shape mismatches are quarantined as well as parse failures. Background task logs are written to workspace-private or per-process private locations with restricted permissions and are bounded and pruned. Settings mutations report persistence status and normalize the active pick so mixed-case selections cannot dangle. Log records and session documents protect timestamps, event names, and names from caller-payload overwrite, and listing caches return copies so callers cannot mutate cached state.

Event and log payloads never carry raw secrets: tool arguments are redacted and truncated before emission. Redaction covers known prefixes, assignment-like syntax including short values after sensitive key names, high-entropy tokens, and exact matches against stored credentials. The structured run log receives event payloads that already exclude raw command output and file contents; the console hands display-worthy observations straight to the renderer instead. Full command output and background-task logs are redacted with the same patterns before they are written to files, so the command header and the payload are treated alike. Redaction matches known shapes only, so those files are still treated as sensitive.

Web fetching validates each redirect hop, refuses private and metadata addresses including alternative numeric encodings, resolves the target host once and pins the connection to the validated address to close the rebinding window, and caps response size before and after decompression.
